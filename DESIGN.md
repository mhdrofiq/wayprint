# Wayprint — Design Document

This document describes Wayprint as it is currently built. Keep it in sync with
the code: when a change alters behaviour, layout, data or API described here,
update the relevant section in the same PR. `PROGRESS.md` holds the history of
how things got this way; this file describes the current state.

## 1. Overview

**Wayprint** is a personal, location-based photo gallery set in Japan. The owner
drops pins on a map and uploads photos to each pin. When a visitor clicks a pin,
the photos burst out of it in an animated explosion (desktop) or slide in as a
stack of prints (phones). The map is public; only the owner can add pins and
photos. Visitors can leave emoji reactions on photos.

It's a spatial photo diary: the map is the organizing principle, and the burst
animation is the signature interaction.

### Goals

- A visually polished, portfolio-worthy personal project.
- Prioritize the **feel** of the burst animation — it is the core experience.
- Work equally well on desktop, tablets and phones (portrait and landscape).
- Low-cost, long-lasting infrastructure for a handful of viewers.

## 3. Data Model

### `pins`

| Column       | Type                    | Description                              |
|--------------|-------------------------|------------------------------------------|
| `id`         | `uuid` (PK, default)    | Unique pin identifier.                   |
| `label`      | `text`                  | Display name (e.g. "Hareruya Ikebukuro"). Max 100 chars (enforced by the API). |
| `lat`        | `double precision`      | Latitude. Must be within 24–46.          |
| `lng`        | `double precision`      | Longitude. Must be within 122–154.       |
| `created_at` | `timestamptz` (default) | When the pin was created.                |
| `updated_at` | `timestamptz` (default) | Set on label edits.                      |

### `images`

| Column          | Type                    | Description                              |
|-----------------|-------------------------|------------------------------------------|
| `id`            | `uuid` (PK)             | Generated by the upload route (also used in the R2 key). |
| `pin_id`        | `uuid` (FK → pins.id)   | Which pin this image belongs to.         |
| `collection_id` | `uuid` (FK → collections.id, nullable) | Collection the image belongs to. `null` = uncollected. |
| `url`           | `text`                  | Public R2 URL of the full-size WebP.     |
| `thumb_url`     | `text`                  | Public R2 URL of the thumbnail WebP.     |
| `caption`       | `text` (nullable)       | Optional caption. Max 300 chars.         |
| `sort_order`    | `integer` (default 0)   | Order within the pin (new uploads are appended). |
| `created_at`    | `timestamptz` (default) | Upload time.                             |

### `collections`

| Column       | Type                    | Description                              |
|--------------|-------------------------|------------------------------------------|
| `id`         | `uuid` (PK, default)    | Unique collection identifier.            |
| `pin_id`     | `uuid` (FK → pins.id)   | Which pin this collection belongs to.    |
| `name`       | `text`                  | Display name. Max 100 chars.             |
| `sort_order` | `integer` (default 0)   | Display order (new collections are appended). |
| `created_at` | `timestamptz` (default) | When the collection was created.         |

### `reactions`

Defined in `supabase/migrations/20260412_reactions*.sql`.

| Column         | Type                      | Description                                    |
|----------------|---------------------------|------------------------------------------------|
| `id`           | `uuid` (PK, default)      | Unique reaction identifier.                    |
| `image_id`     | `uuid` (FK → images.id, cascade delete) | Which image this reaction is on. |
| `emoji`        | `text`                    | A single emoji grapheme (≤16 UTF-8 bytes).     |
| `reactor_name` | `text` (default `'anon'`) | Name the viewer typed. Max 20 chars.           |
| `pos_x`        | `double precision`        | Horizontal position, 0–1 relative to the card (may slightly exceed for overhang). |
| `pos_y`        | `double precision`        | Vertical position, same convention.            |
| `rotation`     | `double precision`        | Degrees, ±8–15° (never near zero).             |
| `created_at`   | `timestamptz` (default)   | When the reaction was added.                   |

### `reaction_rate_limits`

Defined in `supabase/migrations/20260413_reaction_rate_limits.sql`. One row per
reaction attempt: `(id, ip, created_at)`, indexed on `(ip, created_at DESC)`.
Rows older than an hour are removed by the `purge_old_rate_limits()` SQL
function. RLS is on with no policies, so only the service role can touch it.

### Relationships

- `pins` 1 → N `images`, `pins` 1 → N `collections`.
- `collections` 1 → N `images` (`collection_id` nullable; null = uncollected).
- `images` 1 → N `reactions` (at most 15 per image, enforced by the API).
- Deleting a pin cascades to its images and collections in the database.
  **Its R2 files are not deleted** (see §11, known gaps).
- Deleting a collection sets `collection_id` to `null` on its images
  (`ON DELETE SET NULL`) — the photos become uncollected, not deleted.
- Deleting an image deletes its reactions (cascade) and both R2 files.

The `pins`, `images` and `collections` tables and their RLS policies were
created in the Supabase dashboard and are not in `supabase/migrations/`.

## 4. Architecture

```
┌──────────────────────────────────────────────────────────┐
│                     Client (Browser)                     │
│  MapView (MapLibre) · PhotoBurst / Cascade (Framer)      │
│  PhotoLightbox · PinList · AdminSheet / PinEditor        │
└───────────────────────────┬──────────────────────────────┘
                            │ HTTPS
            ┌───────────────┴────────────────┐
            │         Next.js on Vercel      │
            │                                │
            │  Pages (ISR, revalidate 60s)   │
            │   /            /pin/[id]       │
            │   /login (client-only)         │
            │                                │
            │  API routes (app/api/...)      │
            │   pins · burst · collections   │
            │   images (upload) · reactions  │
            └──────┬──────────────────┬──────┘
                   │                  │
            ┌──────▼──────┐    ┌──────▼───────┐
            │  Supabase   │    │ Cloudflare   │
            │  Postgres   │    │ R2 (images,  │
            │  + Auth     │    │ public URLs) │
            └─────────────┘    └──────────────┘
```

### Key Architecture Decisions

1. **Next.js API routes are the backend.** No separate server.
2. **Two Supabase clients.** `lib/supabase.ts` uses the anon key and respects
   RLS; it is used in the browser and for public reads in API routes and
   server components. `lib/supabase-admin.ts` uses the service-role key, bypasses
   RLS, and is only imported server-side (admin mutations, reactions, the
   `LastUpdated` server component).
3. **Uploads go through the API route.** The browser downsizes very large
   images first, then the route runs sharp, uploads both variants to R2, and
   inserts the row.
4. **Pins ship with the page; photos are client-fetched.** `/` is ISR
   (`revalidate = 60`) and renders the pin list into the HTML, so markers need
   no extra request. `/pin/[id]` also embeds that pin's burst data. Server reads
   go through `lib/cached-queries.ts` (`unstable_cache`, 60s), shared query code
   lives in `lib/queries.ts`. Other pins' photos are fetched by the client from
   the cached `/api/pins/:id/burst` route.
5. **Images are served straight from R2.** `next/image` is used with
   `unoptimized`, so Vercel's image optimizer is bypassed and R2's immutable
   cache headers apply.
6. **Admin is one specific Supabase user.** Admin API routes require a valid
   Supabase JWT *and* that the user's id equals `ADMIN_USER_ID`.

## 5. Pages and Routes

| Route         | Rendering | Purpose |
|---------------|-----------|---------|
| `/`           | ISR (60s) | The map, top-left About/Last-updated row, pin list, admin UI when signed in. |
| `/pin/[id]`   | Per request (reads `?c=`), data cached 60s, `notFound()` for unknown pins | Same map, but flies to the pin and opens its burst. Optional `?c=<collection-id>` or `?c=uncollected` pre-selects a collection. Generates per-pin Open Graph / Twitter metadata. |
| `/login`      | Client    | Admin sign-in. Not linked from the map — reached by typing the URL. |

### Permalinks and link previews (`app/pin/[id]/page.tsx`)

- Server-side, the page loads all pins plus this pin's burst data (images with
  reactions, collections) through the 60s server cache, once per request
  (`React.cache`), shared between `generateMetadata` and the page. A pin missing
  from the cached list is re-checked uncached before returning 404, so a
  just-created pin's link works immediately.
- The page preloads the map style and the thumbnails on the burst's first page
  in the HTML head, so they download while the scripts load.
- `?c=<collection-id>` (valid for this pin): title `"<Pin> · <Collection> · Wayprint"`,
  preview image = first photo in that collection, burst opens filtered to it.
- No `?c=`, an unknown `?c=`, or `?c=uncollected`: title `"<Pin> · Wayprint"`,
  preview image = first uncollected photo (or the first photo). `?c=uncollected`
  pre-selects the uncollected view only if the pin actually has uncollected photos;
  otherwise the burst's normal default applies.
- On the client, `MapView` waits for the map's `load` event, flies to the pin
  (zoom 13, 1.2s), then opens the burst at the pin's screen position using the
  embedded burst data. This happens once; clicking other pins afterwards
  behaves normally.

## 6. Use Case Flows

### 6.1 Visitor browses the map

1. The map loads centred on Tokyo with the pins already in the page.
2. Hovering a pin (or pressing it on a touch screen) shows its label in a
   speech-bubble popup and **prefetches** that pin's photos and collections
   (`/api/pins/:id/burst`) into an in-memory cache, then starts downloading the
   thumbnails on the burst's first page, so the burst usually opens instantly.
3. Clicking a pin opens the burst (desktop) or cascade (phones). Map
   interaction (pan, zoom, rotate) is disabled while it's open.
4. Clicking a photo opens the lightbox. Escape, the backdrop, or the close
   control backs out one level at a time.

### 6.2 Visitor uses the pin list

1. Desktop: a frosted "N pins" pill in the top-right. Phones: a small chevron
   tab on the right edge.
2. Opening it shows every pin, newest first, with photo counts.
3. Tapping a pin flies the map there (zoom ≥ 13, never zooming out) and shows
   its label popup until the flight ends. It does **not** open the burst.
   On phones the list closes after a selection.

### 6.3 Visitor shares a link

- **Pin / collection link:** the pin-label pill (desktop) or "Copy URL" button
  in the cascade header (phones) copies `/pin/<id>`, plus `?c=<collection-id>`
  when a collection other than "Everything else" is active. A check mark
  confirms for 1.5s.
- **Image link:** the lightbox "Copy URL" button copies the full-size R2 URL.
- Copying falls back to a hidden textarea + `execCommand('copy')` where the
  Clipboard API is unavailable.

### 6.4 Visitor reacts to a photo

1. Desktop: hover a polaroid and click the `+` in its bottom-right corner.
   Phones: tap the always-visible `+` in the card's top-right.
2. Pick an emoji, then optionally type a name (defaults to "anon") and confirm.
3. `POST /api/images/:id/reactions` — the server validates, rate-limits,
   enforces the 15-per-image cap and picks the sticker position.
4. The sticker appears immediately. Its id is saved in `localStorage`
   (`wayprint_reactions`) so this browser can remove it later: hover + ✕ on
   desktop, tap + confirmation modal on phones.

### 6.5 Admin signs in

1. Visit `/login` directly, sign in with email + password.
2. On return to the map, the admin UI appears: a top-left "Admin" pill on
   desktop, a bottom sheet handle on phones.

### 6.6 Admin adds a pin

1. Open the admin panel and toggle **Edit** on (it turns blue, "Editing").
2. Click an empty spot on the map. `POST /api/pins` immediately creates a pin
   labelled "New Pin" at that spot and selects it in the panel.
3. Rename it in the **Label** field (saves on blur or Enter).

While edit mode is on, clicking a pin selects it in the panel instead of opening
the burst. Clicking the map with a pin selected deselects it.

### 6.7 Admin manages photos

1. Select a pin: from the panel's pin list, by clicking it in edit mode, or with
   the list button in the desktop burst ("Open photo list").
2. Pick a **collection tab** (Uncollected, or a named collection). The photo
   list, the upload target and bulk-move options all follow the active tab.
3. Upload: drop files on the drop zone or browse. Up to 4 upload in parallel;
   a progress bar shows `done / total` (and failures). Skeleton rows stand in for
   each file until it lands. A toast reports the count.
4. Edit a caption (Enter saves, Shift+Enter adds a newline), remove reactions
   (tap an emoji), or delete a photo (trash → confirm).
5. Move photos between collections: **Select** → tick photos (or **Select all**)
   → choose a destination → **Move**.

### 6.8 Admin manages collections

- **Create:** the `+` tab → type a name → Enter/Add. The new tab becomes active.
- **Rename:** edit the name in the bar under the tabs (blur/Enter saves, Escape reverts).
- **Delete:** trash → confirm ("Photos become uncollected").

### 6.9 Admin deletes a pin

"Delete pin" at the bottom of the editor → confirm ("Delete pin and all
photos?"). `DELETE /api/pins/:id` removes the pin and (via cascade) its images,
collections and reactions from the database.

## 7. API Routes

All routes live under `app/api/`. Every `:id` is validated as a UUID first
(invalid → 404). "Admin" means `requireAdmin` (`lib/auth.ts`): a `Bearer`
Supabase JWT whose user id equals `ADMIN_USER_ID`, else 401. The client sends
admin requests through `adminFetch` (`lib/admin-api.ts`).

### Pins

| Method   | Route                | Auth   | Description |
|----------|----------------------|--------|-------------|
| `GET`    | `/api/pins`          | Public | All pins (oldest first) with `image_count`. Cached: `s-maxage=60, stale-while-revalidate=300`. |
| `POST`   | `/api/pins`          | Admin  | Create a pin. `label` (≤100), numeric `lat`/`lng` inside the Japan bounding box. |
| `GET`    | `/api/pins/:id`      | Public | A single pin. |
| `PATCH`  | `/api/pins/:id`      | Admin  | Update `label` (≤100); bumps `updated_at`. |
| `DELETE` | `/api/pins/:id`      | Admin  | Delete the pin (DB cascade; R2 files are left behind). |
| `GET`    | `/api/pins/:id/burst`| Public | `{ images, collections }` for a pin, images with embedded `reactions`, both ordered by `sort_order` then `created_at`. Same cache headers as `/api/pins`. |

### Collections

| Method   | Route                        | Auth  | Description |
|----------|------------------------------|-------|-------------|
| `POST`   | `/api/pins/:id/collections`  | Admin | Create a collection (`name` ≤100), appended to the end. |
| `PATCH`  | `/api/collections/:id`       | Admin | Rename (`name` ≤100). |
| `DELETE` | `/api/collections/:id`       | Admin | Delete; its photos become uncollected. |

### Images

| Method   | Route              | Auth  | Description |
|----------|--------------------|-------|-------------|
| `POST`   | `/api/images`      | Admin | Multipart upload: `file` (image/*, ≤20MB), `pin_id`, optional `collection_id` (must belong to the pin). Processes, stores in R2, inserts the row. Returns 201 with the image. |
| `PATCH`  | `/api/images/:id`  | Admin | Any of `caption` (≤300, non-string → null), `sort_order`, `collection_id`. |
| `DELETE` | `/api/images/:id`  | Admin | Delete both R2 objects and the row. |

### Reactions

| Method   | Route                        | Auth   | Description |
|----------|------------------------------|--------|-------------|
| `POST`   | `/api/images/:id/reactions`  | Public | Add a reaction: `emoji` (single emoji grapheme, ≤16 bytes) and optional `reactor_name` (≤20, default "anon"). Rate limit 5 per IP per 60s (429). Cap 15 per image (409). Server computes `pos_x`, `pos_y`, `rotation`. |
| `DELETE` | `/api/reactions/:id`         | Public | Delete a reaction. There is no server-side ownership check: viewers only see a remove control for ids in their `localStorage`, and the admin editor uses the same route. |

## 8. Visual Language

- **App shell:** the page background is `zinc-700`. The map sits in a card inset
  8px from every edge (`fixed inset-2 rounded-lg overflow-hidden shadow-sm`).
- **Corner radius:** `rounded-lg` is the default for cards, panels, pills on the
  map and inputs. Exceptions: fully round (`rounded-full`) control pills in the
  burst bar, admin pills and tabs; `rounded-2xl` for menus, modals and the empty state.
- **Frosted overlays on the map:** translucent with `backdrop-blur-sm` and
  `shadow-md` — light `bg-white/40` with `text-zinc-700` (Last updated, pin
  list pill, Admin pill) or dark `bg-zinc-800/40` with white text (About).
- **Burst controls:** solid dark `bg-zinc-800` circular/pill buttons with white
  icons, paired with white pills for text (pin label, page counter).
- **Polaroid cards:** warm off-white `#f8f5f0` frame, `rounded-sm`, shadow
  `0 4px 24px rgba(0,0,0,0.28)`. Scatter mode uses a thicker bottom border
  (6/6/20/6px); grid mode uses an even 6px.
- **Typography:** Geist Sans; UI text mostly `text-sm`/`text-xs`;
  section labels in the admin are `text-xs uppercase tracking-wide`.
- **Map popup:** a speech bubble — `maplibregl-popup-content` restyled to
  `rounded-[1.5rem]`, soft shadow, centred single-line label. The MapLibre logo is
  hidden and the attribution is shrunk to 10px at 50% opacity.
- **Safe areas:** `--sat/--sar/--sab/--sal` hold the iOS safe-area insets;
  bottom-anchored UI adds `var(--sab)`. The viewport uses `viewport-fit=cover`.
- **Toasts:** sonner, top-centre, rich colours.

## 9. UI Components

### 9.1 Map (`components/map/MapView.tsx`, `PinMarker.tsx`)

- Full-card MapLibre map. Initial view: Tokyo (35.68°N, 139.69°E), zoom 11.
- Pins are 📍 emoji buttons (`text-2xl`, soft drop shadow), anchored at the bottom.
  They scale to 110% on hover and 125% while selected.
- The label popup appears on hover only while no pin is selected (and briefly
  after flying from the pin list).
- A small "Loading…" pill shows at the top-centre while pins load.
- `MapView` owns all shared state: pins, selected pin and its screen position,
  per-pin photo/collection caches, edit mode, and the admin session.

### 9.2 Top-left overlay row (`AboutPanel`, `LastUpdated`)

A `fixed top-4` flex row with `gap-2`. Its `left` is
`calc(1rem + var(--admin-panel-w))`, so on desktop it slides right of the
Admin pill or open admin panel (animated `left` transition, 300ms).

- **About** — collapsed: dark frosted pill "🗺️ Wayprint". Expanded: a dark
  frosted card (`max-w-xs`) with a one-line description, a × close button, and
  GitHub / LinkedIn pill links (`bg-white/10`, inline SVG icons).
- **Last updated** — light frosted pill, "Updated 7 Apr 2026" (`en-GB` date).
  An async server component: reads the latest `pins.updated_at` and
  `images.created_at` with `supabaseAdmin`, shows the newer one, renders
  nothing if there's no data. Because the page is ISR, it can lag by up to 60s.
- On phones, Last updated hides while About is expanded.

### 9.3 Public pin list (`components/PinList.tsx`)

- **Desktop:** a light frosted "N pins" pill at `top-4 right-4`. Opens a white
  `w-72` panel anchored to the right edge (full height, `rounded-l-lg`) with a
  150ms fade.
- **Phones:** a slim frosted chevron tab, vertically centred on the right edge.
  Opens the same panel below the top row (`top-16`), sliding in from the right
  with a spring; it auto-closes after picking a pin.
- Panel header: "N PINS" + ×. Rows: 📍, label (truncated), photo count.
  Sorted newest first.
- Hidden while a burst is open and, for the admin, while a pin is selected or
  edit mode is on.

### 9.4 Burst switch (`components/burst/PhotoBurstSwitch.tsx`)

Chooses the layout with the media query
`(max-width: 767px), (max-height: 500px)`: phones in either orientation get the
cascade; everything else (desktop, tablets) gets the scatter burst. The query
uses the layout viewport, so iPad pinch-zoom doesn't flip the layout. It is the
same check as `hooks/useIsPhone.ts`, which the switch uses.

### 9.5 Desktop burst (`PhotoBurstDesktop.tsx`, `BurstPhoto.tsx`)

- `bg-black/40` backdrop over the map; clicking it (or Escape) closes the burst.
- Photos are polaroids scattered across the viewport (§10.1) or arranged in a
  grid (§10.2). 18 photos per page.
- Hovering a polaroid lifts it above the others (`zIndex 999`), scales it to
  108% and straightens it. Clicking opens the lightbox.
- While images load and none are cached, a "Loading…" pill sits at the pin.
  If the active filter has no photos, the empty state shows in the centre.
- **Bottom bar** (centred, springs up from below; left to right):
  1. **Collections pill** (only if the pin has collections) — dark pill with
     folder icon, active name and chevron. Opens a white menu above it listing
     "Everything else" (uncollected) then each collection. Choosing one filters
     the burst and resets to page 1.
  2. **Pin label pill** — white, with a link icon; clicking copies the pin
     permalink (§6.3).
  3. **Pagination** (only with more than 18 photos) — ‹ prev, white `X / Y`
     counter, next ›. Changing page plays the full exit then entry animation.
  4. **Open photo list** (admin only) — closes the burst and opens the pin in
     the admin panel.
  5. **Grid / scatter toggle** — grid icon in scatter mode, scattered-prints
     icon in grid mode. All photos re-flow at once (no stagger).
- **Overflow:** if the bar is wider than the viewport minus 32px, the
  collections pill moves to its own row directly above.
- **Default collection:** "Everything else" if the pin has uncollected photos,
  otherwise the first collection. A deep link's `?c=` overrides this.
- **Reaction stickers:** absolutely positioned at the stored `pos_x`/`pos_y`,
  rotated as a unit: a 44px emoji with a hard drop shadow plus a small
  translucent name pill (`rgba(0,0,0,0.35)`, blur, 11px). They may overhang the
  card edge. A `+` button fades in at the bottom-right on hover (hidden at 15
  reactions). Owned stickers reveal a ✕ on hover.

### 9.6 Phone cascade (`PhotoCascadeMobile.tsx`)

- `bg-black/60` backdrop. Tapping anywhere in the cascade outside a card —
  including the header — closes it; so does Escape.
- **Header:** sticky, `bg-black/50 backdrop-blur-sm`, pin label in white
  semibold (truncated) and a translucent "Copy URL" pill (§6.3). In landscape it
  also sticks to the left edge and spans the screen.
- **Portrait:** a vertical stack of large 4:3 cards (§10.3), scrolling
  vertically. **Landscape:** a horizontal strip of cards sized to the screen
  height (§10.4), scrolling sideways; the cards extend up behind the translucent header.
- Cards: `rounded-lg`, 5px `#f8f5f0` frame, softer shadow than desktop.
  Tapping opens the lightbox.
- **Floating bars** at the bottom (spring up): the collections pill
  (`bg-black/40` frosted, `rounded-2xl`, wraps long names) sits above the
  pagination controls. A spacer keeps the last cards clear of them.
- Changing page remounts the cards (replaying the entry animation) and scrolls
  back to the start; so does rotating the phone.
- **Reaction stickers:** emoji only (26px, hard shadow, rotated), in rows of 5

## 10. Animation Specification

The animation should feel **physical, organic and satisfying** — like tossing a
handful of printed photos onto a table. All layout code is in
`lib/burst-layout.ts`. Random values come from a seeded PRNG (mulberry32 seeded
from the pin id), so a pin's layout is stable across re-renders and visits.

### 10.1 Desktop scatter layout

```
thumbSize = 220px (fixed; photos never shrink in scatter mode)
padding   = 60px left/right/top, 110px bottom (clears the bottom bar)

For each photo:
  sample 25 random candidate centres inside the padded viewport
  pick the candidate whose distance to the nearest already-placed centre is largest
  x, y     = that centre minus half the size, clamped to the padded area
  rotation = random −12° … +12°
  zIndex   = random 1 … N   (random stacking order)
```

Overlap is intended — at high counts some is unavoidable, and farthest-point
placement spreads it evenly instead of letting photos pile up.

### 10.2 Desktop grid layout (toggle)

```
gap = 8px, same padding as scatter
cols = max(1, round(sqrt(N × availW / availH))),  rows = ceil(N / cols)
thumbSize = min(220, fit-by-width, fit-by-height)
grid is centred in the available area; a partial last row is centred too
rotation = 0, zIndex = i + 1
```

### 10.3 Desktop motion

- **Container variants:** `open` staggers children by `min(0.04, 0.5 / N)`s;
  `closed` by `min(0.025, 0.3 / N)`s in reverse — so large pages still open
  and close quickly.
- **Each polaroid:** `closed` = centred on the pin, scale 0, opacity 0,
  rotate 0; `open` = its layout position, scale 1, opacity 1, its rotation.
  Spring: stiffness 260, damping 22.
- **Hover:** `scale 1.08, rotate 0, zIndex 999`.
- **Pages:** the photo container is keyed by page inside
  `AnimatePresence mode="wait"`, so the old page collapses into the pin before
  the new one bursts out.
- **Layout toggle:** the `open` targets change in place, so photos spring to
  their new positions together.
- **Bottom bar and menus:** bar rows enter from `y: 40` (spring 300 / 28);
  dropdown menus pop from `y: 6, scale 0.97` (spring 400 / 30).

### 10.4 Phone cascade — portrait

```
photoWidth  = 90% of viewport width,  photoHeight = 0.75 × photoWidth (4:3)
x           = centred, ± random 8px
y           = 72px (header) + i × (0.85 × photoHeight)   → each card shows 85%
rotation    = random −3° … +3°
zIndex      = i (later photos on top)
```

Cards slide in from off-screen left (`x: −viewportWidth`, fade in) with a spring
(stiffness 200, damping 24) and a 50ms stagger, and slide back out to the left on
close.

### 10.5 Phone cascade — landscape

```
photoHeight = max(160, viewportHeight − 12 (top) − bottom bars − 24 − 8)
photoWidth  = 4/3 × photoHeight
x           = 60px + i × (0.85 × photoWidth)
y           = just under the top reservation, ± random 6px
rotation    = random −3° … +3°
```

Cards drop in from 80px above while fading in (same spring and stagger) and
fade out on close. The header stays pinned while the strip scrolls sideways.

### 10.6 Breakpoints

| Condition                                   | Layout |
|---------------------------------------------|--------|
| width ≥ 768px **and** height > 500px        | Desktop scatter burst (220px polaroids; grid ≤ 220px) |
| width < 768px, portrait                     | Vertical cascade (90% width) |
| width < 768px or height ≤ 500px, landscape  | Horizontal cascade (fills height) |

The pin list and admin UI use the same phone query (`hooks/useIsPhone.ts`).

## 11. Image Processing Pipeline

### In the browser (`ImageUploader.tsx`)

1. Files are queued and uploaded **4 at a time**.
2. Any image larger than 2000px on its long edge is redrawn on a canvas at
   2000px and re-encoded as JPEG (quality 0.88) before upload. This keeps
   requests under Vercel's 4.5MB request body limit (a 15MB phone photo becomes
   ~1–2MB). Smaller images are sent untouched.

### On the server (`app/api/images/route.ts`, `lib/image-processing.ts`)

1. Validate: `file` is `image/*` and ≤ 20MB; the pin exists; the collection (if
   any) belongs to that pin.
2. sharp auto-rotates from EXIF orientation, then produces:
   - **Full:** max 2000px long edge, WebP quality 80.
   - **Thumbnail:** max 800px long edge, WebP quality 75 (sharp enough for 220px
     polaroids and the 90%-width phone cascade on high-DPI screens).
   - All metadata (including GPS) is stripped from both.
3. Both go to R2 in parallel under `images/{pin_id}/{image_id}/full.webp` and
   `.../thumb.webp`, with `Cache-Control: public, max-age=604800, immutable`.
4. The row is inserted with `sort_order` = current photo count for the pin.

The route has `maxDuration: 30` (`vercel.json`).

## 12. Performance and Caching

- **ISR pages** (`revalidate = 60`) for `/` and `/pin/[id]`.
- **CDN caching** for `GET /api/pins` and `GET /api/pins/:id/burst`:
  `s-maxage=60, stale-while-revalidate=300`. Changes by the admin can take up to
  a minute to show for other visitors; the admin's own view updates immediately
  from local state.
- **One request per pin:** `/burst` returns images, reactions and collections
  together.
- **Pins in the HTML:** `/` and `/pin/[id]` render the pin list server-side
  (cached 60s via `unstable_cache`); `MapView` only fetches `/api/pins` if the
  server couldn't provide them.
- **MapLibre loads with the page:** `maplibre-gl` is imported statically and
  passed as `mapLib`, so it downloads alongside the other scripts instead of
  after hydration. The map style is preloaded (`preloadMapStyle`) with a
  preconnect to its host.
- **Hover / press prefetch** fills the client-side per-pin cache before a click
  and warms the first page of thumbnails (`lib/preload.ts`).
- **Lightbox** shows the cached thumbnail until the full-size photo loads, then
  preloads its neighbours.
- **Deep links** embed the pin's burst data and preload its thumbnails.
- **Visitors skip admin code:** `AdminSheet` is loaded with `next/dynamic` only
  when signed in, and `useAdminSession` loads the Supabase client only when a
  stored session exists.
- **Server cache** (`unstable_cache`, 60s) for pins, burst data and the
  `LastUpdated` timestamps used while rendering pages.
- **Immutable R2 objects** (keys are UUIDs) cached by browsers for 7 days;
  `next/image` runs `unoptimized` so Vercel doesn't re-process them.
- **Lazy emoji picker** (`next/dynamic`).

## 13. Security

- **Admin auth:** Supabase JWT in `Authorization: Bearer`, validated with
  `supabase.auth.getUser`, and the user id must equal `ADMIN_USER_ID`.
  Sign-ups are disabled in the Supabase dashboard.
- **Database access:** public reads use the anon client (RLS applies); writes use
  the service-role client only after `requireAdmin`. Reactions and rate-limit
  writes also use the service role, behind the API's own validation.
- **Input validation:** UUID check on every `:id`; Japan bounding box and numeric
  types for pin coordinates; length caps (label 100, collection name 100,
  caption 300, reactor name 20); single-emoji check for reactions; image MIME
  type and 20MB size cap for uploads.
- **Abuse limits:** reactions are capped at 15 per image and 5 per IP per minute.
  There is no rate limit on uploads (admin only).
- **Reaction removal** is public with no server-side ownership check. The UI only
  offers removal for reactions this browser created.
- **Privacy:** sharp strips EXIF (including GPS) from stored images.
- **Response headers** (`next.config.ts`, all routes): `X-Frame-Options: DENY`,
  `X-Content-Type-Options: nosniff`, `Referrer-Policy:
  strict-origin-when-cross-origin`, `Permissions-Policy: camera=(),
  microphone=(), geolocation=()`.
- **R2:** objects are public (the map is public). The bucket's CORS policy only
  allows `GET` from `https://wayprint.vercel.app`.

### Known gaps

- Deleting a pin does not remove its photos from R2 (orphaned files).
- The upload route doesn't verify that the decoded file is really an image
  beyond the MIME type; a bad file fails inside sharp with a 500.

### Reaction placement (`lib/reaction-placement.ts`)

The server places each new sticker: it samples 40 candidates along the four
edges of the photo area (inside the polaroid frame), jittered up to 12% inward
and 7% outward (the overhang), and picks the one farthest from existing
stickers (random for the first). Rotation is ±8–15°.
